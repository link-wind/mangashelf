## Context

见 proposal.md。当前 `manga.resolve` 同步采集整话并由 API 在任务结束后上传全部截图，阅读器只收到一份一次性清单；Python 固定任务协议已有 JSONL 进度通道，DESIGN §12.2 与 §18.1 允许服务端逐页生成对象 Key、由 Java 上传私有对象。

## Goals / Non-Goals

**Goals:**

- 把 `Pages` 响应扩展为可选渐进字段：会话 ID、总页数、逐页 URL 占位、完成状态与错误；旧源继续使用原字段。
- 用一次浏览器采集进程按页输出就绪事件；API 在收到事件时校验截图并上传，会话保留到采集结束，阅读器轮询状态。
- 首屏只等页数与首批页图，消失的页位显示「加载中」，失败后保留已就绪页图并展示明确错误。

**Non-Goals:**

- 不新增数据库表、队列、WebSocket 或通用任务框架；不为每页启动浏览器。
- 不改变 MangaDex、拷贝漫画、规则源的整章清单行为；不规避哔哩登录、购买与解锁限制。
- 不解决截图对象的 TTL/GC，也不试图在用户离开页面后立即取消正在运行的采集。

## Decisions

- 采集会话放在 API 进程内，以章节 URL 复用；现有单并发信号量用于浏览器进程，后台线程负责等待 Python 任务，避免 HTTP 工作线程被整话采集占住。进度行携带页号及任务目录内的相对文件名，仍符合 stdout JSONL 协议。备选的「每页独立 HTTP 任务」会重复启动浏览器且无法保持原站页位。
- 服务端为每次采集生成不可枚举的会话 ID，使用配置桶和 `captured/{会话}/{页号}.png` 固定 Key；只接受会话内已登记的页号。前端得到相对读取 URL，读取端点继续要求登录并返回 `private, no-store`。备选的前端直接接收对象 Key 会扩大输入面。
- 扩展现有 `Pages` 记录而非另建 API：缺省渐进字段时前端按旧行为一次渲染；哔哩返回总页数的占位数组，`null` 表示加载中。前端轮询会话状态时只替换新就绪的 URL，保留当前页、滚动位置和进度。备选的 SSE 需要新增连接和超时治理。
- 最终成功仍要求连续页序与全部 PNG 有效；超时、缺页、页数未知或非公开章节均写入会话错误，阅读器显示错误但保留已加载的页。这样渐进显示不会把残缺章节伪装成完成。
- 会话在完成后保留短暂缓存供重复打开，失败会话不缓存为成功清单；进程重启后会话失效，下一次请求重新采集并明确重新加载。

## 2026-11-12 实测补记

- 显式失败的任务若沿用 `status: SUCCEEDED` 包装会导致 `PythonTaskRunner` 在 `result.json` 之前结束，统一外壳现按任务返回的 `status` 写结果并返回非零退出码；采集后台线程据此展示失败而保留已就绪页图。
- 逐页 PNG 先写临时文件再原子改名；服务端在页图上传完成前不会把该页标为就绪。前端以会话 ID 固定续读位置，轮询只合并新 URL，避免新页到达重置当前页或重发章节目录请求。
- 站内截图 URL 使用 `/api/v1/external-manga/captured/...` 同源前缀，图片代理回退逻辑跳过这些相对路径；未登录仍被拒绝，响应为 `private, no-store`。

## Risks / Trade-offs

- 上游渲染或网络抖动 → 已就绪页仍可读，缺页明确报错并保留原站入口；不静默重试到伪装成功。
- 轮询产生额外请求 → 只在采集未完成期间按秒级间隔查询，完成或失败后停止。
- API 进程重启或内存会话过期 → 阅读器收到明确失效状态并可重新打开；不把旧对象 Key 当作长期资产。
- 临时目录与对象在后台任务期间存在 → 任务结束即清理本地文件；成功对象沿用现有 M35 留存边界，后续单独处理清理策略。

## Migration Plan

以扩展字段方式部署：旧前端忽略新增字段仍可读取完整清单；新前端识别渐进字段后按页显示。回滚时移除前端轮询并恢复同步等待整章采集即可，已有对象 Key 格式不变。无数据库迁移。
