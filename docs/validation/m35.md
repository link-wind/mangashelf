# M35 哔哩公开章节站内阅读验证

2026-11-11。基线 `6390ae1`，工作区变更 `restore-bilibili-reader`。

使用独立 Compose 项目 `mangashelf-bili-check` 重建 API、Worker 和 Web 镜像。PostgreSQL、RabbitMQ、SeaweedFS 使用新卷，API 和 Web 绑定隔离的回环端口。对象存储预先建独立私有桶，并通过 `S3_BUCKET` 指定，开发栈不受影响。

回归：Java 23 个单测通过；前端生产构建通过；`processing/.venv/bin/python -m unittest processing.tests.test_bilibili_capture` 的 3 项 Chromium 测试通过，覆盖并页顺序、缺页失败和滚动加载。

**验收状态：真实公开章节尚未采全。** 受控样本只证明 MangaShelf 内部链路可用，不能替代上游实测。首页继续走原站，未新增章节列表；取得匿名浏览器可完整渲染的真实章节后，需要在同一全栈环境复验到末页与历史续读。成功截图对象尚无生命周期清理策略。

## 2026-11-11 真实章节再验

- 原站第 3 页有画面，第 4 页起进入加密页图加载流程；旧浏览器启动方式下，加载器在 CDN 请求发出前就返回错误。匿名普通 Chrome 的同一章能渲染第 19、20 页，没有发现这一章要求登录或购买的提示。
- 改用普通 Chromium 和回补流程后，本地真实 MangaShelf API 返回 20 张顺序正确的 PNG，匿名读取被拒，已登录响应为 `private, no-store`。浏览器显示并解码第 20 页；从历史返回仍在最后一组，PostgreSQL 中进度为 20/20。
- Docker Desktop 全局内存上限设为 4 GiB。较低的 API 单容器上限曾触发 Chromium 子进程 OOM；该次隔离测试未通过，不计为真实 Docker 验收。

## 2026-11-11 首页与全栈验收

- [《航海王》官方目录](https://manga.bilibili.com/detail/mc24742)返回 1,199 条章节，数量与原站详情声明一致；196 条同时标为免费且未锁定。第 004 话对应章节 ID `218098`。界面默认列公开可读章节，「显示全部」保留其余章节的原站链接。
- 本地开发栈和隔离 Docker 栈均实测「漫画首页 → 哔哩漫画 → 航海王 → 004 → 第 20 页 → 历史继续阅读」。API 返回 20 张顺序正确的 PNG；读取要求登录，响应禁止共享缓存。末页解码成功，真实 PostgreSQL 的两次验收记录均为 20/20。
- 隔离栈六服务运行，Docker Desktop 保持全局 4 GiB，验收服务额度合计 3,328 MiB；API 额度调至 1,664 MiB，本次没有 OOM。验收时关闭了 Worker 的可选嵌入模型以给 Chromium 留出空间。
- Java 23 个单测、3 项 Chromium 采集测试、前端生产构建与 OpenSpec 严格校验通过。采集仍依赖原站稳定性；如果到截止时间未凑齐全部页，返回首个缺页，保留原站入口。

## 2026-11-12 渐进加载

- OpenSpec 变更 `progressive-bilibili-reader` 把原先「等整话 20 页全部采完才返回」改为一次浏览器采集、逐页就绪：确认总页数后立即建立固定页位，采集任务通过 JSONL 进度输出页号，API 校验 PNG 并逐页上传到配置桶，阅读器轮询会话并替换对应页图。未就绪页显示「第 N 页 · 加载中…」；只有页序连续且全部有效才标记采集完成。
- 本地真实链路冷启动《航海王》第 005 话：首次章节请求 2.71 秒返回 `capturing` 与 20 个页位，阅读器显示加载中占位；随后观察到 1/20、10/20、20/20 页逐步就绪，全部 PNG 有序、要求登录且响应为 `private, no-store`。本地《航海王》第 004 话从首页进入 1,199 话目录，采集 1/20、10/20、20/20 逐步完成，翻到第 20 页，历史「继续阅读」恢复到末页并写入 PostgreSQL 进度 20/20。
- 隔离 Docker 全栈在全局 4 GiB 内存下重验：首页进入哔哩站内目录，第 008 话首次响应为 `capturing`，加载中占位可见，按 1/20、10/20、20/20 渐进就绪，末页解码与历史续读通过；API 容器无 OOM。另以不存在章节验证页数无法确认时返回 `502 CAPTURE_PAGE_COUNT_UNKNOWN`，阅读器显示明确错误，不交付部分清单。
- 回归：Java 23 个单测、5 项 Python 测试（含按页就绪事件与任务显式失败保留结果清单）、前端生产构建、OpenSpec 严格校验与 `git diff --check` 通过。成功截图对象仍沿用现有留存边界；后续单独处理 TTL/GC。
