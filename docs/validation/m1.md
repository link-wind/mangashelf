## 2. Worker 中断恢复实验（DESIGN 11.3 / 21.1）

1. 以 60 页带噪点大图触发 chapter.parse（解析耗时 > 3s）；
2. 解析进行中 `kill -9` Worker（attempt 1 中断于 16/60）；
3. 租约（120s）过期后 API 侧恢复扫描介入：任务回 QUEUED，追加 outbox 派发记录
   （dispatch_no=2，publisher confirm 后标记 DISPATCHED）；
4. Worker 重启后消费重派发消息，attempt 2 全量重跑，产物与页面在同一事务重建；
5. 终态：job SUCCEEDED attempt=2，revision READY page_count=60；
   事件序列完整（中断前 16 条 → "租约过期，重新派发" → 重跑 64 条 → result）。

旧 attempt 无法覆盖新结果：提交匹配 (status='RUNNING', lease_token)；恢复派发幂等（dispatch_no 递增）。

## 3. 重大实测发现：AWS SDK 默认校验和导致对象污染 ⚠️ 已修复

**现象**：浏览器阅读器图片全部加载失败，但同 URL `fetch` 返回 200、curl 下载"成功"。
**根因**：AWS SDK for Java v2 当前默认启用灵活校验和（CRC32），`putObject` 以
`aws-chunked` 传输编码上传；**SeaweedFS 3.96 不解码该编码，把 `896;chunk-signature=…`
分帧字节连同 `Content-Encoding: aws-chunked` 原样入库**，对象实际内容被污染。
M0 冒烟只检查了下载状态码与任务内摘要（内存侧对比），未用解码器打开下载文件，因此未暴露。
**修复**：S3Client 显式 `requestChecksumCalculation(WHEN_REQUIRED)` +
`responseChecksumValidation(WHEN_REQUIRED)`；修复后对象以 `RIFF….WEBP` 开头，PIL 正常解码。
**流程改进**：M1 起验收增加"下载产物必须经图像解码器打开"的检查；该发现同样回应
DESIGN 24.1-3 —— "S3 兼容"不代替逐项能力验证。

## 5. 过程中的工程修复（全部在真实环境暴露）

| 问题 | 修复 |
| --- | --- |
| Boot 4：裸 flyway-core 不触发自动配置 | 改用 `spring-boot-starter-flyway` |
| 组合外键首次写法引用了不存在的列 | `FOREIGN KEY (id, current_revision_id) REFERENCES chapter_revisions (chapter_id, id)` |
| chapter.parse 目标与 V1 `upload_session_id NOT NULL` 冲突 | V2 `DROP NOT NULL` + 按任务种类 CHECK |
| PG JDBC 不推断 Instant 参数 | 统一 `JdbcTime.t()` 转 OffsetDateTime |
| Security 7 `DaoAuthenticationProvider` 需构造器注入 | 构造器传入 UserDetailsService |
| XOR CSRF 委派模式与 Cookie 仓库往返 403 | 改用纯 `CsrfTokenRequestAttributeHandler` |
| CurrentUser record 未实现 Serializable → 会话序列化 500 | `implements Serializable` |
| 页序调序撞 (revision_id, ordinal) 唯一键 | 事务内先整体平移再落位 |
| SDK aws-chunked 污染对象（本节第 3 项） | 校验和回退 WHEN_REQUIRED |
